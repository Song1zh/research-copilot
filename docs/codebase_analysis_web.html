Research Copilot 研究文档问答系统：代码逐模块解析

这份文档解释项目目标、入口文件、请求链路、核心模块职责和扩展方向。 它按照源码结构组织，重点回答四个问题：项目做什么、功能如何实现、每个模块负责什么、后续可以如何扩展。

1. 项目做什么

这个项目是一个面向科研文档的 RAG 问答系统。它不是通用聊天机器人，而是把本地文献库中的 PDF 解析成 evidence chunks，再基于这些 evidence 生成可追溯、结构化、带引用编号的回答。

核心目标

  • 支持本地 PDF 文献库加载和索引。
  • 把 PDF 全文按论文 section 切成 chunk，并写入 Chroma 向量库。
  • 检索 top-k evidence，约束模型只能基于 evidence 回答。
  • 用 Pydantic schema 约束输出结构。
  • 校验回答里的 [E1]、[E2] 是否真实存在。
  • 提供 FastAPI 接口和 Streamlit 本地 Demo。

当前产品线

文献库 Agentic RAG 读取本地论文库 manifest，索引已有 PDF，并使用混合检索和可选知识图谱增强问答。

这个项目的工程价值在于闭环完整：文献库管理、PDF 解析、索引、混合检索、结构化输出、证据校验、知识图谱、Demo 和测试都已经串起来。

3. 核心入口

app/main.py

FastAPI 服务入口

这是项目最重要的后端入口。它创建 FastAPI 实例，定义请求模型，注册异常处理器，并提供文献库索引、文献库问答和图谱状态接口。

主要接口

  • GET /health：健康检查，确认服务可用。
  • GET /literature/papers：读取文献库 manifest 并返回论文清单。
  • POST /literature/index：解析本地 PDF，构建 Chroma 文献库索引，可选构建 Neo4j 图谱。
  • POST /literature/ask：运行文献库 Agentic RAG。
  • GET /literature/graph/entities：读取 Neo4j 图谱实体统计。
  • GET /literature/graph/relations：搜索 Neo4j 图谱关系路径。

demo/streamlit_app.py

Streamlit 本地 Demo 入口

这个文件提供用户界面，适合演示。它直接导入核心函数运行：索引文献库、文献问答、查看图谱状态、构建和搜索知识图谱。

app/cli.py

命令行演示入口

CLI 有两个模式：llm 直接调用模型，workflow 运行 toy workflow。这个文件主要用于早期学习和快速调试，不是主业务入口。

4. 文献库 Agentic RAG

文献库功能把项目从“问一篇文档”升级成“问一批本地论文”。它的核心思想是先把 PDF 文献库索引成可检索 chunk，再围绕用户问题执行多步检索和证据融合。

5.1 文献库索引流程

读取 manifest CSV 生成 PaperRecord 过滤已有 PDF 加载 PDF 文本 按 section 切 chunk 写入 Chroma

入口是 index_literature_corpus()。它先调用 load_paper_records()，读取 paper_manifest.csv、core_paper_inventory.csv 和 local_reaxff_manifest.csv。

当前正式文献库是 PDF-only。metadata-only 论文只保留在候选清单里，不进入 Chroma 索引和 Neo4j 图谱。这个设计是为了保证回答可以追溯到原文 evidence。

5.2 Agentic RAG 工作流

核心函数是 run_literature_agent_workflow()，位于 workflows/literature_agent_workflow.py。 它的 LangGraph 节点如下：

节点职责实现方式
question_analyzer判断问题类型，抽取材料、方法、性质关键词基于关键词规则，如 RDX、HTPB、ReaxFF、decomposition
query_planner生成检索计划写入 trace，说明要用 hybrid retrieval 和 KG retrieval
hybrid_retriever检索文本 evidence向量检索 + 关键词检索融合
kg_retriever检索 Neo4j 图谱上下文按 query terms 查询 Paper 到实体的关系
evidence_fusion去重融合证据用 paper_id::chunk_id 作为唯一 key
answer_generator生成结构化回答构造 evidence + KG prompt 调用 LLM；失败时降级为模板回答并记录 trace
citation_verifier检查 evidence 引用复用 citation alignment 检查
self_reflection补充局限性证据少或引用未通过时写入 limitations

5.3 混合检索为什么重要

向量检索适合语义相近的问题，但对 ReaxFF、CL-20、HTPB 这类专业术语不一定稳定。 所以项目额外实现了关键词检索，再通过 vector_weight=0.6 和 keyword_weight=0.4 合并分数。

5. 普通 RAG vs 知识图谱 RAG

普通 RAG 和知识图谱不是谁替代谁，而是解决不同层面的问题。本项目中，Chroma 负责找原文 evidence， Neo4j 负责表达论文、材料、方法、力场、软件、性质和发现之间的结构化关系。

维度普通 RAG知识图谱
数据形态 文本 chunk，例如 Methods 或 Results 中的一段原文。 节点和边，例如 (Paper)-[:USES_FORCE_FIELD]->(ReaxFF)。
查询方式 把用户问题转成向量或关键词，在 Chroma 里找相似片段。 用实体词在 Neo4j 里查 Paper-实体-关系路径。
擅长问题 “这篇论文怎么说”“原文证据是什么”“总结这几个片段”。 “哪些论文研究了 RDX”“哪些论文用了 ReaxFF”“材料-方法-性质之间有什么连接”。
优势 证据直接、实现简单、能保留原文上下文。 关系清楚、适合跨论文统计、适合结构化检索和路径展示。
局限 不擅长跨文献关系推理，可能出现 retrieval drift。 依赖抽取质量，当前项目是规则式抽取，不等于完整语义理解。
本项目的 KG 是增强层：普通 RAG 先用 Chroma 找可引用的原文 evidence，知识图谱再用 Neo4j 补充“论文和实体之间是什么关系”。 最终回答仍优先保留 evidence citation 约束，避免图谱关系脱离原文证据。

当前实现完成后的用户体验

  • 在“知识图谱”页可以连接 Neo4j、构建图谱、查看实体统计。
  • 可以搜索 RDX、ReaxFF、HTPB 等实体，看到 Paper -> Entity 关系路径。
  • 文献问答结果中会显示“知识图谱命中”表格；Neo4j 不可用时会明确说明本次只用了文本 RAG。

6. 模块逐个解析

下面按目录逐个解释主要文件。每个模块都写清楚“做什么、怎么实现、被谁调用”。

6.1 app 目录

app/main.py

做什么：提供 HTTP API，是后端服务入口。

怎么实现：定义 FastAPI app、请求模型、异常 handler 和多个路由。路由内部不直接写复杂逻辑，而是调用 workflows 或 core 函数。

关键点：/literature/index、/literature/ask 和 /literature/graph/* 组成文献库问答与图谱演示闭环。

app/cli.py

做什么：命令行演示工具。

怎么实现：用 argparse 读取 --mode、--query、--trace，然后选择直接调用 LLM 或 toy workflow。

6.2 core 目录：基础能力

core/config.py

做什么：统一配置中心。

怎么实现：加载 .env，读取 DashScope/OpenAI-compatible 配置，定义项目根目录、Chroma 路径、文献库路径和 Neo4j 配置。

注意：这里会自动创建 CHROMA_DB_PATH 和 APP_DATA_DIR，文献库 PDF 仍来自 manifest 指向的本地目录。

core/document_loader.py

做什么：加载 txt、md、pdf 文档，返回统一的 LoadedDocument。

怎么实现：文本文件使用 UTF-8、UTF-8-SIG、GB18030、GBK 逐个兜底；PDF 用 pypdf.PdfReader 提取每页文本；最后统一换行和空行。

被谁调用：论文加载器 paper_loader 和文献库索引链路。

core/text_splitter.py

做什么：把长文本切成自然边界 chunk。

怎么实现：不是简单硬切，而是在目标切点附近优先找换行、中文标点、英文标点、空格。每个 chunk 记录 chunk_id、文本起止位置和 metadata。

core/section_splitter.py

做什么：面向论文，把全文按 Abstract、Methods、Results、Conclusion 等章节识别后再切 chunk。

怎么实现：用正则匹配短标题行，识别 section；References 会跳过，避免参考文献污染检索。

价值：用户问“方法是什么”时，section metadata 能帮助后续检索和展示。

core/vector_store.py

做什么：封装 Chroma 向量库。

怎么实现：优先使用 chromadb.PersistentClient 持久化到磁盘；如果失败则退化为内存 client。自定义 LocalHashEmbeddingFunction，保证没有外部 embedding 服务也能运行 Demo。

重要取舍：本地 hash embedding 可离线运行，但语义效果有限，适合教学和工程闭环演示，不适合生产级检索。

core/retriever.py

做什么：统一向量检索入口。

怎么实现：创建 ChromaVectorStore，调用 query()，把结果整理成 evidence 列表。

core/keyword_retriever.py

做什么：关键词检索。

怎么实现：从 Chroma 取出全部 chunks，用正则分词，按类似 BM25 的方式计算关键词得分。

适合场景：专业术语、材料名、方法名、缩写词。

core/hybrid_retriever.py

做什么：融合向量检索和关键词检索。

怎么实现：分别执行两种检索，对分数做 min-max 归一化，用加权和计算 hybrid score，再按分数排序。

core/evidence_formatter.py

做什么：把检索结果转换成前端和 LLM 都能理解的 evidence 格式。

怎么实现：按顺序生成 E1、E2，截断 snippet，保留 chunk_id 和 source_path。

core/evidence_checker.py

做什么：检查回答中引用的 evidence id 是否真实存在。

怎么实现：用正则提取 [E1]、[E1,E2]，和 answer.evidence 中的 id 集合对比，输出缺失引用、非法引用和未使用 evidence。当前会检查 summary、methods、findings、limitations、mechanisms 以及对比表 finding。

core/schema_parser.py

做什么：解析 LLM 返回的 JSON，并用 Pydantic schema 校验。

怎么实现：先剥离 Markdown 代码块或模型输出中的额外文本，再分别解析通用研究回答和文献库回答。文献库主链路使用 parse_literature_answer() 校验 LLM 输出。

core/citation_verifier.py

做什么：更细粒度地评估 claim 和 evidence snippet 的文本支撑关系。

怎么实现：抽取中英文 token，计算 claim 与 evidence snippet 的重合词，给出 supported、weak_supported、unsupported 等标签。

状态：这是轻量文本匹配，不是完整语义蕴含判断。

core/error_codes.py

做什么：保留通用错误码和失败输出 helper。

怎么实现：定义 ErrorCode 枚举，提供 build_error_info() 和 build_failure_output()。当前文献库问答主链路对 LLM 失败采用 generation_mode 和 llm_error 表达降级状态。

core/api_response.py

做什么：统一 API 成功和失败响应。

怎么实现：生成 request_id、UTC timestamp、latency_ms，并返回 ApiResponse。

core/llm_client.py

做什么：封装大模型调用。

怎么实现：读取 DASHSCOPE_API_KEY、OPENAI_BASE_URL、OPENAI_MODEL，创建 OpenAI client，调用 chat.completions.create()。

core/logging_config.py

做什么：统一日志配置。

怎么实现：日志同时输出到控制台和 logs/app.log。

6.3 core 目录：文献库和图谱能力

core/literature_manifest.py

做什么：读取论文清单并统一成 PaperRecord。

怎么实现：读取多个 CSV，兼容不同字段名，按 paper_id 和 DOI 去重，支持按 category 和 priority 过滤。

core/paper_loader.py

做什么：把 PaperRecord 加载成 PaperDocument。

怎么实现：如果有 PDF，就调用 load_document() 提取全文；如果没有 PDF，则构造 metadata 文本。不过正式索引当前会跳过 metadata-only。

core/literature_indexer.py

做什么：构建文献库 Chroma 索引。

怎么实现：加载 PDF-only records，调用 load_paper_document() 和 split_paper_document()，再把 chunks 写入 Chroma。

core/simulation_extractor.py

做什么：从论文 chunk 中抽取领域实体。

怎么实现：用固定词表和正则识别材料、方法、力场、软件、条件、性质和发现句子。每个抽取结果都保留 evidence chunk id 和 evidence text。

core/graph_store.py

做什么：封装 Neo4j 写入和查询。

怎么实现：创建唯一约束，写入 Paper、EvidenceChunk、Material、Method、ForceField、Software、Property、Finding 节点和关系；关系边保存 evidence_chunk_id 和 evidence_text，查询时统一格式化 path_text。

core/literature_graph_builder.py

做什么：从论文 chunks 构建 Neo4j 图谱。

怎么实现：先调用 extract_from_chunks() 抽取结构化实体，再逐条写入 Neo4jGraphStore。

core/kg_retriever.py

做什么：按关键词从 Neo4j 取图谱上下文。

怎么实现：查询 Paper 到实体的关系行，返回 paper_id、title、relation、entity_label、entity_name、evidence_chunk_id、evidence_text 和 path_text。Neo4j 不可用时返回 available=false，不阻塞文本 RAG。

6.4 workflows 目录

workflows/literature_agent_workflow.py

做什么：文献库 Agentic RAG 主流程。

怎么实现：把问题分析、检索计划、文本检索、图谱检索、证据融合、LLM 回答生成、引用校验和自我反思拆成明确节点。LLM 只负责基于 evidence 和 KG context 生成结论，真实 evidence、query_plan 和 kg_context 由后端固定注入。

workflows/toy_workflow.py

做什么：LangGraph 学习原型。

怎么实现：包含理解问题、生成回答、格式化输出三个节点，展示如何维护 state 和 trace。

6.5 schemas 目录

schemas/literature_answer.py

schemas/simulation_extraction.py

做什么：定义图谱抽取实体结构，如材料、方法、力场、软件、模拟条件、性质和发现。

schemas/api_response.py

做什么：定义 API 外层响应结构。

schemas/schemas.py

做什么：早期 toy workflow 使用的通用结构化回答 schema。

scripts/run_literature_eval.py

做什么：面向文献库问答的评测脚本。

7. 数据结构和响应契约

文献库回答结构

{
  "summary": "基于混合检索证据，并结合 Neo4j 图谱关系... [E1,E2]",
  "comparison_table": [],
  "mechanisms": ["... [E1]"],
  "limitations": [],
  "methods": ["... [E2]"],
  "findings": ["... [E3]"],
  "evidence": [
    {
      "evidence_id": "E1",
      "chunk_id": 5,
      "source_path": ".../sample.pdf",
      "snippet": "..."
    }
  ],
  "kg_context": {
    "available": true,
    "items": [
      {
        "paper_id": "P1",
        "title": "Example paper",
        "relation": "USES_FORCE_FIELD",
        "entity_label": "ForceField",
        "entity_name": "ReaxFF",
        "evidence_chunk_id": "P1:12",
        "evidence_text": "The simulations used ReaxFF...",
        "path_text": "(Paper: P1) -[:USES_FORCE_FIELD]-> (ForceField: ReaxFF)"
      }
    ]
  },
  "generation_mode": "llm",
  "llm_error": null
}

生成模式：generation_mode="llm" 表示 LLM 成功生成；template_fallback 表示 LLM 不可用或输出未通过 JSON/schema/citation 校验，系统使用模板降级；no_evidence 表示没有检索到证据，因此没有调用 LLM。

API 外层响应

{
  "success": true,
  "code": "OK",

8. 错误处理和证据校验

项目的错误处理不是简单抛异常，而是尽量返回前端可消费的结构化结果。文献问答中，LLM 是主生成器，但不是唯一出口；模型不可用、JSON 不合法、schema 不匹配或 citation alignment 失败时，会降级为模板回答，并在 generation_mode 和 llm_error 中说明原因。

场景系统行为前端信号
LLM 正常返回并通过校验使用模型生成的结构化回答generation_mode="llm"
没有检索到 evidence不调用 LLM，返回证据不足说明generation_mode="no_evidence"
API Key 缺失、模型调用失败、JSON/schema/citation 校验失败降级为模板回答，保留真实 evidence 和 KG contextgeneration_mode="template_fallback"，llm_error 有值
Neo4j 不可用继续文本 RAG，不阻塞问答kg_context.available=false

引用校验

check_answer_evidence_alignment() 检查三件事：

  1. summary、methods、findings、limitations、mechanisms 和对比表 finding 是否都带 citation。
  2. 引用的 E# 是否存在于 evidence 列表中。
  3. 哪些 evidence 没被回答引用。

这一步能防止模型编出 [E9] 这样的假引用，也能暴露回答没有引用证据的问题。

11. 可扩展方向

1. 替换真实 embedding

当前 hash embedding 保证离线运行，但语义质量有限。可以接入 DashScope embedding、OpenAI embedding、BGE 或本地 sentence-transformers。

2. LLM 输出评测

当前 LLM 已参与最终回答生成。后续可以增加离线题集评测，统计 citation alignment、JSON 解析失败率、模板降级率和人工可用性。

3. 增加 reranker

在 hybrid retrieval 后加入 cross-encoder 或 LLM rerank，提高 top-k evidence 质量，减少 retrieval drift。

4. 增强 citation verifier

当前主要是引用 id 和词面支撑检查。可以升级为 claim-level 语义蕴含判断，区分“引用存在”和“引用真的支持结论”。

5. API 分层重构

app/main.py 已经偏大。后续可以拆成 routers、services、dependencies，使后端结构更接近生产工程。

6. 文献库增量索引

目前索引更多是全量 upsert。后续可以按文件 hash、mtime 或 manifest 版本做增量更新。

12. 面试讲法

可以用下面这段话概括项目：

我实现了一个面向 PDF 文献库的科研问答系统，基于 FastAPI、Chroma、Pydantic、Streamlit、LangGraph、OpenAI-compatible LLM 和 Neo4j，打通了 manifest 管理、PDF 解析、section-aware chunking、混合检索、LLM 结构化回答、evidence 引用校验、Agent trace 和知识图谱关系查询。

如果被问“你最核心的工程设计是什么？”

可以回答：我没有让模型直接自由回答，而是把回答限制在检索出来的 evidence 上，并用 schema 和 citation alignment 做二次约束。这样前端能稳定消费结果，后端也能知道失败发生在哪个阶段。

如果被问“项目现在的不足是什么？”

可以回答：当前本地 hash embedding 主要服务 Demo 可运行性，语义检索能力有限；LLM 输出虽然有 schema 和 citation alignment 约束，但 citation verifier 还不是严格语义蕴含判断；知识图谱抽取仍是规则式。这些都是下一步优化方向。
